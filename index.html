IThe Method

Four movements, in order. Scanners cannot form assumptions; hunters who skip modelling cannot test them.

00

Saturation & Recency Targeting

New code is undertested code. Every control was written in response to something — controls are strongest where attacks already happened and weakest where the feature is young.

  • Read the disclosed record. Each report names a patched class and, more valuably, the style of mistake this engineering team makes.
  • Where a platform permits no disclosure, say so — silence is not evidence of a clean surface.
  • Hunt recency: changelogs, mobile release diffs, job postings, published packages, frontend feature flags still dark.
  • Everyone tries /v1/. Try /v3/ before it is announced.
01

Target Modelling

Understand the machine before attacking it. Four models, written down, before a single fuzzed request.

  • Identity — how identity is established versus how it is carried, and where it is re-derived versus trusted from the request.
  • Tenancy — what the isolation unit is, and where tenants touch. Boundaries are strong in the middle and weak at the seams.
  • Value — how value enters, moves, and leaves. The exit path is the crown jewel.
  • State — every multi-step flow, its transitions, and what the server actually checks at each one.
02

Attack the Assumptions

Every model implies something the developers took for granted. Each assumption is a hypothesis. This phase is the experiment — root cause first, payload second.

  • Be able to state why the code is wrong before testing it. If you cannot, you are guessing.
  • Two accounts, always. Object from A, credential from B — that is the test.
  • Move the identifier: path, query, body, header, claim. Different layers validate differently.
  • Send it twice with different values. If authz reads one and the fetch reads the other, that is the bug.
03

Verify the Final State

Never verify the response. Twenty 200s can apply once. An error response can still commit the transaction. A 403 can arrive after the side effect.

  • Balance manipulated? Read the balance endpoint and the ledger, from a fresh session.
  • Cross-tenant access? Fetch the object as its real owner and diff.
  • Privilege escalated? Perform an action only the higher role can perform.
  • A finding not confirmed against ground truth is a hypothesis, not a bug.
IIThe Saturation Law

Duplicate probability is proportional to mechanical discoverability. The easier a bug is to find by machine, the more hunters have already found it. Climb the ladder until the crowd thins to nobody.

IIIThe Doctrines

Eight root causes. Each states why the code is wrong, not what to type. Techniques expire; causes recur.

01

Identity & Object Ownership

Authorization is checked at the wrong layer, or on the wrong value. The server confirms who you are and forgets to confirm whether the object is yours.

anywhere an object identifier crosses a trust boundary

02

Trust Boundaries Between Services

The edge authenticates and normalises; internal services trust the edge. Any input reaching a service without passing that check is fully trusted input.

gateways, service meshes, BFF layers, internal admin tooling

03

Financial & Accounting Logic

Money is not a number. Every system moving value must hold an invariant — value created equals value destroyed. Arithmetic and ordering break it at the edges.

deposit, withdrawal, conversion, fees, refunds, settlement

04

State Machines & Workflows

Step N validates by reading a flag step N−1 wrote, rather than re-deriving the fact. Control the flag and the prerequisite evaporates.

onboarding, KYC tiers, 2FA enrolment, password reset, checkout

05

Race Conditions

Check-then-act. A condition is validated and acted upon as two operations with a window between them. Structure, not request spam.

coupons, rewards, limited stock, withdrawals, uniqueness checks

06

Batching & Per-Object Authz

Authorization validated at resolver entry, then the ORM sweeps up everything with a single IN clause. Aliases and transport arrays multiply it.

GraphQL mutations, alias batching, JSON query batching

07

Key Trust & Token Lifecycle

The server lets the token name its own key, and the token outlives the authority that issued it. alg:none is the shallow end.

jku/x5u/jwk/kid handling, refresh reuse, post-revocation validity

08

Injection & Input Handling

Input reaches a sensitive sink unparameterised, or the server fetches a URL without validating the resolved destination.

only where the model says user input actually reaches the sink

VIThe Rules
01

Critical and High only — unless a lesser link is required to complete a Critical chain, in which case report the chain.

02

Root cause before payload. State why the code is wrong before testing it.

03

Prove it or drop it. Every finding ships with a weaponised, reproducible PoC.

04

Verify the final state, never the response.

05

One target, deep. Build tooling alongside the hunt.

06

Fold, don't collapse. A new idea joins the map; it does not become the map.

07

Document as you go — tools, rationale, and dead leads, with dates.

Rules of engagement

These are production systems with real users. The method is restraint, not noise.

  • No destructive payloads. Risk ceiling stays at 2 on production; manual verification preferred over automated exploitation entirely.
  • No abusive volume. Aggressive thread counts read as denial of service and get accounts banned.
  • No real-user data. Prove a PoC with two accounts I control, or prove access without exfiltrating.
  • No persistence, no lateral movement, no denial of service. Prove reachability, then stop.
  • Read the program policy before the first request.
  • Only test systems with explicit written authorization.
